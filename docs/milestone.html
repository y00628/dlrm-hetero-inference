Work Completed

The full DLRM pipeline (bottom MLP, embedding lookup and pooling, feature interaction, top MLP + sigmoid) is implemented in our CPU reference. The GPU implementations currently cover embedding lookup and pooling only.

  • Datasets: Synthetic Zipf trace generator with three sizes (tiny 5 MB, small 2 GB, medium 10 GB), plus converters for Meta production traces and a 1 TB Criteo click-log slice.
  • CPU reference: Complete OpenMP + AVX2 pipeline, up to 8 threads. Serves as the correctness reference and CPU baseline.
  • Single-GPU engine: Embedding lookup and sum pooling with coalesced accesses across the embedding dimension.
  • CPU–GPU memory tiering:
    • GPU zero-copy (baseline): The GPU reads hot rows from device memory and cold rows directly from mapped host memory over PCIe.
    • CPU partial pooling: CPU threads sum cold rows with AVX2 and send one partial-sum vector per bag, and the GPU adds the hot rows.

Preliminary Results

All approaches pass the correctness check against the CPU reference. Hardware: CMU GHC node, Intel i7-9700 (8 cores, 15 GiB RAM), NVIDIA RTX 2080 (8 GB), PCIe 3.0 x16. Batch size is 2048 throughout.

Partial pooling wins when many cold IDs live in host memory, since it sends one vector per bag over PCIe. At high cache fractions few rows are cold, so zero-copy wins while partial pooling still pays for CPU processing and the partial-sum transfer.

Primary Concerns

No dataset we can run gives tables that are both realistic and the right size. MLPerf multi-hot Criteo is realistic, but the preprocessed set is ~163 GB with no partial download, and its largest tables (~20 GB each) exceed our 8 GB VRAM, 15 GB host RAM and storage quota. The datasets we can run are too small: the Meta file has 8 tables totalling 0.43 GB, and the Criteo slice is a single-lookup (L=1) 48 MB part file, so both fit on one GPU and never force tiering. We plan to look for additional datasets and generate synthetic configurations that meet our benchmarking needs.
